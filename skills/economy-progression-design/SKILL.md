# Economy and progression design

Keep economy generic and evidence-led. The GDD may describe currencies, sources, sinks, ordering, and visible feedback without supplying numeric tables. Observed values are constraints; missing values are generated by the agent, stored in config, and validated through the playable loop. Do not require a price sheet merely to start implementation.

## Method
1. Extract only evidenced constraints and relationships from the reference.
2. Build features with tunable config fields and one deterministic balance source; leave unobserved numeric tuning unset until the balance pass.
3. Simulate, play from a clean save at normal time, measure reachability and feedback, then adjust automatically within the chosen guardrails.
4. Preserve observed ordering, rarity feel, unlock dependencies, and UI states even when absolute values are regenerated.
5. Keep one multiplier/composition path, typed numeric storage, and display formatting separate from gameplay values.
6. Record generated assumptions and validation results, not a second hand-authored economy specification.

## Balance the whole loop, not a table
Every balance variable is coupled: zone access, boss chase/recovery, tool effectiveness, egg difficulty, hit cadence, training gain, pet income, capacity, rewards, ads, and IAP. Tuning one isolated table can break the loop. Therefore:
1. Keep **one deterministic formula source** (code + config) for the whole chain and a simulator/audit that reads it; every change re-runs the audit.
2. Define **target horizons** with the human (e.g. full completion in a stated number of days; first session, day 1, week 1 goals) and check each against the simulation. The game must not end too quickly: onboarding, session, day-scale and long-term collection goals all need content.
3. Learn **relationships and rhythm** from the reference (monotonic zone speeds, readable rarity jumps, late pets creating discrete income jumps), not its absolute numbers.
4. Measure real values in Play Mode (hit cadence from the actual animation clip, travel distances from real geometry, measured income uplift from size/mutation) before accepting a model; a provisional guess falsely showed near-zero boss exposure.
5. Fast-forward is only a QA accelerator: `normal duration = QA duration / timeScale`. Judge balance on normalized time and on a **fresh save**; a polluted save is valid only for runtime smoke checks.
6. Monetization guardrails are part of balance: rewarded ads are recovery/temporary acceleration, interstitials only at natural breaks with cooldown, IAP is utility/cosmetic value; none replaces the progression loop or forms a forced paywall.
7. Verify with assertions (monotonic speeds, price growth, multiplier bounds) in an editor audit and keep results in `docs/balance/`.

## Tuning checklist
- Are all required sources and sinks reachable?
- Does the loop preserve the reference's relative rhythm without dead ends or runaway growth?
- Do generated values remain monotonic where the reference is monotonic and bounded where feedback would otherwise explode?
- Test with a fresh save and a representative mid-game save; report assumptions separately from observed facts.
