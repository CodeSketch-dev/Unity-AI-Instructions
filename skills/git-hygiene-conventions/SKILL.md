# Git hygiene conventions

Why: in a 2k-commit mobile project, about 4% of commits were `.`/`update`/`doing`, versions were reused, there were no tags, main went stale while a game branch was the real trunk (350 merges), one scene was edited 85 times, and generated files churned in every commit. These conventions prevent the same drift. Standing rule of this studio: commit, push and branch only when the owner asks; agents may prepare messages, hooks and scripts, and must not run history-rewriting commands without explicit approval.

## 1. Commit message format (`references/commit-format.md`)
- Subject: `[vX.Y]: Area: what changed` (version marker of the build in progress) or `type(area): what changed` with type in feat, fix, perf, refactor, chore, docs, test, build, revert. English, imperative, >= 6 chars, no `.`/`update`/`doing`/`wip`.
- Body (when the change is not trivial): one bullet per class or asset group, saying the behaviour AND the why (`Ads_NativeGate: skip native after tutorial level 20 because ...`). Annotations: `TWEAK:` balance numbers, `ATTENTION:` risky change.
- One logical change per commit. Keep these separate commits: mass renames/moves (no logic edits), dead-feature removal, generated-file refreshes, `.gitignore` edits, lean deletions (one category each).
- Hook sample: `scripts/commit-msg` (install with `git config core.hooksPath tools/githooks`).

## 2. Versioning and release tagging (`references/release-tagging.md`)
- One source of truth for version and build number (project settings plus a small config asset); the build number only increases; remote-config keys live beside it.
- Every build handed to testers or stores gets an annotated tag `vX.Y.Z` on the exact commit; never reuse a version string.
- Release notes are generated from commits since the previous tag: `scripts/release_notes.py`.
- Cadence that worked: a release about every two weeks; ship risky features dark behind a remote flag and enable remotely.

## 3. Branches
- ONE live trunk (main) that always builds. Short feature branches (days, not months), rebased or merged back often. A long-lived variant branch needs an explicit sync list (which commits must be ported), not "(Need In X)" notes in messages.
- If the real work lands on a game branch, make that branch the trunk (rename) instead of letting main rot.
- Binary or giant files (scenes at 85 edits, 28 MB font atlases) are conflict magnets: split scenes into prefabs, force text serialization, keep generated assets out of feature commits.

## 4. Generated-file hygiene (`references/generated-files.md`)
- Isolate or ignore: TMP font atlases (rebuild on demand), `link.xml`, solution/project files, localization tables regenerated from csv, graph/index tool output, screenshots written by Editor hotkeys, build reports.
- Never let `.gitignore` swallow runtime assets: template globs (`Demo*`, `Sample*`, `Tutorial*`, `Example*`) hide first-party folders; test a clean clone (`repo-hygiene-gitignore-audit`).
- Track `.meta` files always; track `packages-lock.json` so git-sourced packages are reproducible; keep `ProjectVersion.txt` tracked.
- Generated code/assets carry a header (`// GENERATED by <tool>, do not edit`) and the tool is idempotent.

## 5. Scheduled sweeps (`references/dead-asset-sweep.md`)
- Every ~2 weeks (and before each release): run the dead-asset proof (`lean-asset-audit`), review DEAD-PROVEN rows, delete in a dedicated commit per category.
- Whole-feature removal is one commit containing code, prefabs, assets, tests and the doc line; never leave a half-removed feature behind.
- Churn report per release: `scripts/churn_report.py --tag-range vA..vB` (top 20 files) to spot hubs and giant scenes; low-info subject count as a hygiene KPI.

## 6. Pre-merge / pre-release checklist
Compile clean, EditMode PASS/SKIP equal to baseline, missing-script/reference check 0 (`house-editor-tools`), clean-clone check (clone to a temp folder, open, compile, diff `git ls-files` with the working tree), banner/native/loading overlay smoke on a device for ad changes, low-end profile run (FPS) at each tag.

## Pitfalls
- Version strings reused for different builds make crash reports ambiguous.
- A mass rename mixed with logic edits cannot be reviewed or reverted: separate commits, compare tests before/after.
- Editor-only mocks hide device bugs (ads close/hide calls): test ads and native on a device early.
- History rewrite to shrink a big pack is an owner decision; propose, never run.
- Merge noise: prefer rebase for short branches; do not merge main into a variant daily without the sync list.
